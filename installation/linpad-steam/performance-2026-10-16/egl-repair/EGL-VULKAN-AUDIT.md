# Software EGL and the separate Vulkan driver

The physical game process on LinPad 4445 now confirms the intended driver selection: auxiliary Mesa 25 EGL/Gallium is loaded while Unity selects Mesa 26 Venus on the Apple M2 GPU. The same run subsequently logs a guest null-address SIGSEGV before any verified game frame. This note incorporates the parent-operated device reports; the audit itself performs no device action.

`LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe` and `MESA_LOADER_DRIVER_OVERRIDE=swrast` select the software GL/Gallium route. The first two controls are documented together by [Mesa](https://docs.mesa3d.org/envvars.html#gallium-driver). The actual Venus 26 ELF contains none of these three environment-name strings; Gallium 25 contains all three. Venus's dynamic dependencies contain no EGL, GL, Gallium, LLVM or GBM library. Literal-string inspection is supporting evidence, not a complete proof of all transitive behavior.

The Vulkan loader is separately directed to the Mesa 26 Venus JSON by `VK_ICD_FILENAMES`. The manifest names `libvulkan_virtio.so`; the established search order is EGL prefix, Mesa 26 prefix, then base runtime. The EGL payload contains no Vulkan library, so this order resolves the Mesa 26 Venus file before the older base copy. `VK_DRIVER_FILES` must remain unset because it takes precedence over `VK_ICD_FILENAMES`. The Khronos loader documents both [driver selection and filename resolution](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Loader/main/docs/LoaderDriverInterface.md). `MESA_VK_WSI_DEBUG=sw` is retained from the already validated cube configuration; it is not a new fallback ICD selection.

The exact [ELF readout](egl-vulkan-elf-readout.txt) and [hashes/comparison](egl-vulkan-elf-audit.json) show that the added EGL prefix has no library filename collisions with either existing prefix. EGL 25 explicitly requires `libgallium-25.0.7-2+deb13u1.so` and reuses the base GBM 25. Venus 26 does not depend on those private Mesa components. Both routes still share public libdrm, Wayland, XCB and related libraries; the existing Mesa 26 prefix overrides several base versions. That order was also used by the passing software EGL probe. This reduces the identified private-ABI mixing risk, but it does not establish that every combined-process code path is compatible.

The [combined-process excerpt](combined-game-excerpt.txt), tied to the original report hashes in [provenance](combined-game-provenance.json), closes the selection gate for game PID 5681. Unity records `Vulkan renderer=[Virtio-GPU Venus (Apple M2 GPU)]`, vendor `106b`, device `1b000008`, and `venus (22), Mesa 26.2.4-1` at 10:54:08 UTC. The 10:54:55 map snapshot contains `/opt/hollow-mesa26/.../libvulkan_virtio.so` alongside `/opt/hollow-egl/.../libEGL_mesa.so.0.0.0` and `libgallium-25.0.7-2+deb13u1.so`, plus base LLVM 19 and GBM 25. The earlier 10:52 snapshot lacked Venus, but this later snapshot resolves that evidence gap.

At 10:54:22.545 UTC Unity logs `Caught fatal signal - signo:11 code:1 errno:0 addr:(nil)`. The parent then stops the remaining process manually; exit 137 is the later stop result, not the original failure. The observed driver selection establishes that software EGL controls did not redirect this run to a software Vulkan renderer. It does not establish general Mesa coexistence correctness, the cause of the guest fault, rendered gameplay or FPS.
